# ADR-0008: Environments

- **Status:** Accepted
- **Date:** 2026-05-04
- **Slice:** 1

## Context

We need predictable answers to: where do I test a change against real Stripe? where do I demo to the owner? where does production traffic go? Mixing environments is the source of every "I just wiped the wrong database" incident.

## Decision

Four environments. Each has its own Vercel deployment, Supabase project, Stripe keys, Twilio number (or sandbox), and Resend domain.

### `local` (each developer)

- Next.js dev server on localhost:3000
- Supabase: `supabase start` local stack (Docker), seeded from `supabase/seed.sql`
- Stripe: **test mode**, with Stripe CLI forwarding webhooks to localhost
- Twilio: test credentials, no real SMS sent
- Resend: sandbox mode, all emails routed to a single dev inbox
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=local`, sampling 0% (no events sent)
- PostHog: dev project, separate from prod analytics

### `preview` (per pull request)

- Vercel preview deploy auto-created on every PR
- Supabase: shared `staging` project — every preview hits the same DB
- Stripe: **test mode**
- Twilio: sandbox; SMS deliveries logged but not sent to live numbers
- Resend: sandbox
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=preview`
- PostHog: dev project

Caveat: shared staging DB means PRs can interfere with each other. Acceptable for early-stage; we'll add ephemeral preview DBs in Slice 4 if it bites.

### `staging` (deployed from `main` automatically)

- Vercel: dedicated `staging.<domain>` deployment (or `staging-mopc.vercel.app` if no custom domain yet)
- Supabase: `staging` project (same one preview uses)
- Stripe: **test mode** (still — staging is not for real money)
- Twilio: real number, real SMS — staff QA sends test SMS to themselves
- Resend: production-grade, custom from-address, deliveries to real addresses
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=staging`, full sampling
- PostHog: dev project

Used for: owner UAT before each slice goes to production, DR-drill restores, load testing.

### `production`

- Vercel: production deployment, custom domain (`membersonlypokerclub.com`)
- Supabase: `production` project, daily backups + PITR enabled, paid tier
- Stripe: **live mode** — real money
- Twilio: A2P 10DLC-registered production number
- Resend: production
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=production`, errors paged to on-call
- PostHog: production project (separate from dev)

### Promotion policy

- `local → preview`: PR open
- `preview → staging`: PR merge to `main`
- `staging → production`: Manual promotion via Vercel "promote to production" after owner UAT (or fully-automated with smoke-test gate from Slice 4 onward)

### Visual indicators

- Non-production environments display a thin banner across the top: `LOCAL` (purple), `PREVIEW` (yellow), `STAGING` (orange). Production has no banner. Prevents staff from running real refunds against staging because they thought they were in prod.

### Database access

- Production DB access is restricted to **Vercel functions + the owner's account**. No developer has direct production credentials.
- Staging DB credentials are shared with the developer team, stored in 1Password.
- Local DB credentials are auto-generated by `supabase start`.

### Deployment-hygiene checklist (amendment owned by ADR-0034)

Three timestamp-substrate verifications gate every environment promotion (`local → preview`, `preview → staging`, `staging → production`). All three are owner-action checks; CI cannot fully automate them because they touch vendor-side configuration (Stripe Dashboard) and base-image version skew that lives outside the repo.

**1. Stripe account timezone MUST be UTC** (per ADR-0034 §"Vendor-derived moments"):
   - On every environment that has its own Stripe account (test mode for `local`/`preview`/`staging`; live mode for `production`), open the Stripe Dashboard → Settings → Business → "Timezone" and confirm value is **UTC**.
   - If a Stripe Connect onboarded account in the future ships with a non-UTC timezone, the dashboard render path that displays vendor-supplied moments will warn on DST-window transitions per ADR-0034's vendor-moment rules — but the audit row is still UTC. Document any non-UTC connected account in a journal entry citing this checklist.
   - **Promotion blocker:** If a new Stripe account is created (e.g. for a second club), the operator MUST set its timezone to UTC before the first live charge. Confirmed by a screenshot in the promotion journal entry.

**2. Postgres image tzdata version pinning + patch-cadence tracking** (per ADR-0034 premortem-risk-10):
   - Supabase Postgres images bundle their own tzdata. When the image is upgraded (Supabase initiates the upgrade window; we don't control timing), tzdata may change with legislative DST rule updates (e.g., a country abolishing DST, the EU's recurring proposal, US DST-repeal bills).
   - **Staging is the canary.** Every Postgres image upgrade lands on the `staging` Supabase project at least one promotion window before production. If staging-vs-production tzdata version skew is observed (via `SELECT version FROM pg_timezone_abbrevs LIMIT 1;` or `SHOW timezone_abbreviations;`), a journal entry MUST document the skew and an `audit-render` regression test MUST be run against the spring-forward and fall-back instants in `tests/time/audit-render.test.ts` on the staging image before production accepts the same upgrade.
   - **Pinning artifact:** the current Supabase Postgres major version is documented in `supabase/config.toml` under `[db].major_version`. Patch-level tzdata is NOT pinned (Supabase manages it) but the major-version pin prevents silent upgrades.
   - **Cadence tracking:** when Supabase announces a Postgres image rollout, log the rollout date + tzdata version into a journal entry tagged `[deployment-hygiene]`. This gives a paper trail when a DST-rule change later surfaces a render-correctness bug.

**3. Database role/session timezone MUST be UTC** (per ADR-0034 §"Storage and database rules"):
   - The Supabase Postgres session timezone is set to UTC at the role/database level. Application code, migrations, `psql` sessions, BI tools, and replicas all observe `SHOW timezone;` → `UTC` unless they explicitly `SET timezone = ...`.
   - **Verification command (run from the Supabase SQL editor or `psql` on each environment):**
     ```sql
     SHOW timezone;
     SELECT current_setting('timezone'), now() AT TIME ZONE 'UTC' AS utc_now;
     ```
     Expected: `timezone` = `UTC`. If the value drifts (e.g. to `US/Central` or a region default), all `date_trunc('day', x)` queries silently switch buckets. The day-bucket SQL lint (`scripts/lint/sql-day-bucket.mjs`) catches the missing `at time zone` clause in application code, but cannot catch a server-side default drift.
   - **Promotion blocker:** every promotion (especially production) verifies this query before traffic flips. Document the result in the promotion journal entry.

These three checks are the **deployment-side mitigation** for ADR-0034's vendor-derived-moments + tzdata-substrate-divergence risks. The complementary application-side mitigations (`lib/time/` helpers, ESLint `no-restricted-syntax` rule, `scripts/lint/sql-day-bucket.mjs`) live in the repo and run on every PR; the three checks here cover the parts of the substrate that the repo cannot enforce on its own.

**Annual audit:** at the start of each calendar year (or on any major Postgres image rollout), re-run all three checks against every environment and log the results in a `docs/journal/<YYYY-01-NN>-deployment-hygiene-annual-audit.md` entry. This catches slow drift (e.g. a Stripe account that was correct at creation but flipped during a vendor-side migration).

## Consequences

**Positive:**

- Clear answer to "which DB am I editing" at all times.
- Stripe test/live separation prevents accidental real charges in dev.
- Owner can UAT staging without touching production data.

**Negative:**

- 4× the secrets to manage. Vercel handles per-env env vars cleanly; we accept the surface area.
- Staging Supabase costs $25/mo (Supabase Pro tier). Considered necessary.

## Alternatives considered

- **Single staging environment, no preview deploys.** Loses the per-PR review URL. Rejected — it's free with Vercel and saves QA time.
- **Production = `main` branch with no staging.** Owner UAT happens in production behind a feature flag. Considered for cost reasons; rejected because some ADRs (DR drills) need a non-production target to safely restore into.
