# ADR-0008: Environments

- **Status:** Accepted
- **Date:** 2026-05-04
- **Slice:** 1

## Context

We need predictable answers to: where do I test a change against real Stripe? where do I demo to the owner? where does production traffic go? Mixing environments is the source of every "I just wiped the wrong database" incident.

## Decision

Four environments. Each has its own Vercel deployment, Supabase project, Stripe keys, Twilio number (or sandbox), and Resend domain.

### `local` (each developer)

- Next.js dev server on localhost:3000
- Supabase: `supabase start` local stack (Docker), seeded from `supabase/seed.sql`
- Stripe: **test mode**, with Stripe CLI forwarding webhooks to localhost
- Twilio: test credentials, no real SMS sent
- Resend: sandbox mode, all emails routed to a single dev inbox
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=local`, sampling 0% (no events sent)
- PostHog: dev project, separate from prod analytics

### `preview` (per pull request)

- Vercel preview deploy auto-created on every PR
- Supabase: shared `staging` project — every preview hits the same DB
- Stripe: **test mode**
- Twilio: sandbox; SMS deliveries logged but not sent to live numbers
- Resend: sandbox
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=preview`
- PostHog: dev project

Caveat: shared staging DB means PRs can interfere with each other. Acceptable for early-stage; we'll add ephemeral preview DBs in Slice 4 if it bites.

### `staging` (deployed from `main` automatically)

- Vercel: dedicated `staging.<domain>` deployment (or `staging-mopc.vercel.app` if no custom domain yet)
- Supabase: `staging` project (same one preview uses)
- Stripe: **test mode** (still — staging is not for real money)
- Twilio: real number, real SMS — staff QA sends test SMS to themselves
- Resend: production-grade, custom from-address, deliveries to real addresses
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=staging`, full sampling
- PostHog: dev project

Used for: owner UAT before each slice goes to production, DR-drill restores, load testing.

### `production`

- Vercel: production deployment, custom domain (`membersonlypokerclub.com`)
- Supabase: `production` project, daily backups + PITR enabled, paid tier
- Stripe: **live mode** — real money
- Twilio: A2P 10DLC-registered production number
- Resend: production
- Sentry: `NEXT_PUBLIC_SENTRY_ENV=production`, errors paged to on-call
- PostHog: production project (separate from dev)

### Promotion policy

- `local → preview`: PR open
- `preview → staging`: PR merge to `main`
- `staging → production`: Manual promotion via Vercel "promote to production" after owner UAT (or fully-automated with smoke-test gate from Slice 4 onward)

### Visual indicators

- Non-production environments display a thin banner across the top: `LOCAL` (purple), `PREVIEW` (yellow), `STAGING` (orange). Production has no banner. Prevents staff from running real refunds against staging because they thought they were in prod.

### Database access

- Production DB access is restricted to **Vercel functions + the owner's account**. No developer has direct production credentials.
- Staging DB credentials are shared with the developer team, stored in 1Password.
- Local DB credentials are auto-generated by `supabase start`.

## Consequences

**Positive:**

- Clear answer to "which DB am I editing" at all times.
- Stripe test/live separation prevents accidental real charges in dev.
- Owner can UAT staging without touching production data.

**Negative:**

- 4× the secrets to manage. Vercel handles per-env env vars cleanly; we accept the surface area.
- Staging Supabase costs $25/mo (Supabase Pro tier). Considered necessary.

## Alternatives considered

- **Single staging environment, no preview deploys.** Loses the per-PR review URL. Rejected — it's free with Vercel and saves QA time.
- **Production = `main` branch with no staging.** Owner UAT happens in production behind a feature flag. Considered for cost reasons; rejected because some ADRs (DR drills) need a non-production target to safely restore into.
