# ADR-0017: CI/CD

- **Status:** Accepted
- **Date:** 2026-05-04
- **Slice:** 1

## Context

Every PR must be checked before merge, every merge must deploy, and rollback must be one click. The team is small (1–2 developers) and the production surface area is non-trivial: real money flows through Stripe, schema changes hit a single shared Postgres, and the marketing site, member portal, cashier console, and admin all share one Next.js deployment (ADR-0001). The pipeline must give us per-PR review URLs, gate merges on a real test gauntlet, and apply database migrations safely against production without manual ssh-into-the-DB toil.

Vercel's git integration alone gives us preview deploys, but it does not run typecheck, lint, unit, integration, e2e, or Lighthouse — those have to live somewhere. GitHub Actions is the natural home because the repo already lives on GitHub, secret scanning is already enabled there (ADR-0007), and Actions is free for public repos and inexpensive for private.

## Decision

**CI runs in GitHub Actions; CD runs in Vercel; database migrations apply via the Vercel deploy hook.** Branch protection on `main` enforces that the two pipelines have agreed before code reaches production.

### CI — GitHub Actions (`.github/workflows/ci.yml`)

Triggered on every PR and every push to `main`. Steps run in order; any failure blocks the merge:

1. `pnpm install --frozen-lockfile`
2. `pnpm typecheck` (`tsc --noEmit`)
3. `pnpm lint` (ESLint + Prettier check)
4. `pnpm test` (Vitest unit + integration; coverage gate per ADR-0021)
5. `pnpm test:e2e` (Playwright against the Vercel preview URL — depends on the preview deploy succeeding)
6. Lighthouse CI (perf, a11y, SEO budgets per ADR-0030; vanilla `lhci` driver)
7. Merge blocked if any step fails

Backstop greps from other ADRs (the `*_cents` schema rule from ADR-0004, the service-role-key boundary check from ADR-0007) run inside step 3 or as dedicated steps in the same workflow.

### CD — Vercel

- Every push to a branch produces a **preview deploy** (per ADR-0008 `preview` environment, hitting the shared staging Supabase project).
- Every push to `main` auto-deploys to **staging** (`staging.<domain>` per ADR-0008).
- Production is reached by **manual promotion** from staging via the Vercel dashboard, after owner UAT. From Slice 4 we may automate the staging→production hop behind a smoke-test gate.

### Database migrations

Migrations live in `supabase/migrations/NNNN_<name>.sql` and are **forward-only** — no down migrations, rollback is a forward fix. Migration safety rules (zero-downtime ordering, `CREATE INDEX CONCURRENTLY`, NOT-NULL backfill split) are enforced by the `MIGRATION-REVIEW` checklist defined in ADR-0018.

Production migrations apply through the **Vercel deploy hook**: the deploy step runs `supabase db push` against the target project before swapping traffic to the new build. A migration failure rolls back the deploy. Production migrations are gated on staging migration success — staging always runs the migration first as part of the auto-deploy from `main`.

### Rollback

- **Application:** Vercel "redeploy previous" — instant, one click.
- **Database:** forward-fix migration. PITR restore is the last resort (ADR-0019).

### Branch protection on `main`

- 1 PR review minimum (revisit at >1 developer).
- All CI checks passing.
- Branch up-to-date with `main` before merge.
- **Signed commits required** (commit-level, not just tags — keeps provenance auditable for regulated-data work).
- Direct push to `main` is allowed only by the owner for emergency hotfix and is logged.

### Secrets in CI

GitHub Actions reads only the secrets it needs (preview Supabase URL, Stripe test keys, Lighthouse token) via repository-scoped Actions secrets — never production secrets, which live in Vercel only (ADR-0007). Nothing in CI ever touches a production credential.

> **Open question:** whether to add `release-please` for changelog automation. Defer until we have a release cadence worth automating.

> **Open question:** whether to require 2 reviewers once the team grows past 1 developer. Trigger: onboarding the second engineer.

> **Open question:** rollback policy for a migration that succeeds on staging but fails on production after partial application. Default position is forward-fix per ADR-0018, but the runbook (Slice 4, ADR-0027) needs the explicit playbook.

## Consequences

**Positive:**

- Every PR ships with a live preview URL the owner can click. No "works on my machine" arguments.
- Merge to `main` is a single gate: green CI + Vercel deploy → staging is current. There is no out-of-band step to forget.
- Migrations applying through the deploy hook means a schema change and the code that depends on it ship together; we cannot deploy code that references a column that doesn't exist yet.
- Forward-only migrations remove the temptation to "just run the down migration" against prod, which is how production data dies.
- Lighthouse + a11y budgets in CI prevent the marketing site from regressing on the metrics ADR-0030 commits us to.

**Negative:**

- **GitHub Actions is a single point of failure.** A multi-hour Actions outage stops all merges. Mitigation: branch protection's "up-to-date" rule can be bypassed by the owner for genuine emergencies; we accept the rare hour-of-friction over the cost of running a second CI provider.
- **Vendor concentration.** GitHub Actions + Vercel + Supabase deploy hook means three SaaS services participate in every production deploy. ADR-0031 covers the portfolio-level posture; for CI/CD specifically, the migration-application step is the most painful to re-platform if Vercel disappears.
- **Secret leakage surface.** Adding Actions to the secret distribution list (alongside Vercel and Supabase) doubles the rotation work each cycle. Mitigation: Actions only ever holds non-production secrets; rotation cadence stays per ADR-0007.
- **Deploy throughput.** The full pipeline (install → typecheck → lint → test → e2e → Lighthouse) runs ~6–10 minutes on a clean cache. Acceptable for a 1–2 person team merging a handful of PRs per day; revisit (parallelize stages, split workflows by path filter) if median PR-to-merge time exceeds 20 minutes.
- **Branch protection friction.** Required signed commits will trip up any contributor without GPG/SSH signing set up. Mitigation: `CONTRIBUTING.md` documents the one-time setup; the cost is a single onboarding step.
- **Migration safety windows.** Because migrations run during the deploy, a slow migration extends deploy time and can lock tables. ADR-0018's zero-downtime rules (no long-locking ops, `CREATE INDEX CONCURRENTLY`, batch backfills) are the load-bearing mitigation; CI cannot detect a slow migration without a shadow DB (ADR-0018 open question).

## Alternatives considered

- **GitLab CI instead of GitHub Actions.** Stronger pipeline DSL, better matrix-build ergonomics, and decouples CI from the GitHub provider. Rejected — the repo already lives on GitHub, the team already uses GitHub PR review, and moving CI to a third party introduces a webhook/round-trip path between PR comments and CI status that Actions has natively.
- **Vercel git integration only, no GitHub Actions.** Simpler — Vercel deploys on every push and runs `vercel build`. Rejected because Vercel does not natively run Vitest, Playwright, Lighthouse, or repository-level grep checks. We would end up writing a `vercel build` shell script that re-implements CI badly.
- **Husky pre-commit / pre-push hooks instead of CI checks.** Faster feedback, no remote round-trip. Rejected as the *primary* gate — hooks can be bypassed with `--no-verify`, do not run in PRs from forks, and don't help when a second developer's machine has a different Node version. We may add a thin Husky layer locally for typecheck + lint as a developer convenience, but the merge gate stays in CI.
- **Single shared staging environment, no per-PR previews.** Cheaper (one Vercel deploy slot), simpler URL routing. Rejected per ADR-0008 — preview-per-PR is free with Vercel and the per-PR review URL has been the single highest-leverage QA tool on prior projects.
- **Out-of-band migration runner (cron job, manual `supabase db push`).** Decouples migration timing from deploy timing — useful if a migration genuinely needs a maintenance window. Rejected as the default because the coupling between code and schema is the whole point; deploys that fail on migration apply are a feature, not a bug. Maintenance-window migrations remain available as a manual escape hatch documented in the runbook (ADR-0027).
