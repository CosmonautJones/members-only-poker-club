# Conductor run — ADR-0036 payment management console (Slice 1)

## Context

Payment substrate without Stripe. ADR-0036 ratified 2026-05-15 in the same batch as ADR-0035 (admin operations console); the v1 surface ships seven tables (`payments`, `memberships`, `time_wallets`, `time_ledger`, `disputes`, `stripe_webhook_events`, `refund_requests`), an authority-matrix guard, an idempotent fail-loud refund-initiation server action, the `/admin/payments` overview shell, and the new-refund form — all gated behind ADR-0010 (Stripe account activation + live keys), which is owner-action-blocked. Slice 1's job was to compose every load-bearing piece of the design surface that is NOT contingent on a live Stripe key, so that Slice 2 (the webhook handler + real `stripe.refunds.create` call) can land as a thin shell over an already-tested substrate.

The opportunity recognized at planning time: most of the design surface is substrate, not Stripe-coupled. Schema, RLS, authority matrix, audit-action taxonomy, idempotency-key plumbing, refund-form UI, error boundary, and the `PAYMENTS_CONSOLE_READY` flag flip can all ship and be exhaustively tested with pglite + Stripe mocks; only the actual `stripe.refunds.create()` invocation and the webhook handler need the live key. The fail-loud posture (`assertStripeConfigured()` throws `StripeNotConfiguredError` AFTER the audit row commits) means the manager-facing surface is wired end-to-end today and the only thing missing in Slice 2 is the env-var flip + the Stripe call replacement.

The run end-to-end: spec-writer + critic (one revision — pinned the `member_id → profile_id` repo-consistency deviation, the `roleAtLeast` placement question, the AC28 parent-error-boundary typo, and the audit-event-taxonomy off-by-one) → planner (`.conductor/36/plan.json`, 13 tasks t1–t13 — t1 was renumbered from t0 at plan revision time so there is no t0) → four premortem dispatches across the schema / RLS / authority / fail-loud surfaces (44 risks total, synthesized to a single worker-actionable document at `.conductor/36/premortem-synthesis.md` with six cross-cutting decisions D1–D6 plus per-task pointers) → six worker waves (1: t1 payments+memberships schema in parallel with t6 authority + t7 Stripe-boundary errors + t8 audit-action constants; 2: t2 time-bank schema + t3 disputes/webhook/refunds schema; 3: t9 initiateRefund server action; 4: t4 RLS policies; 5: t5 RLS contract tests + t10 overview page + t11 refund-new page; 6: t12 console-availability flip + t13 docs/integration test; +1 cross-task t8-respawn after wave 4 to fix the audit-event-taxonomy + dashboard-cache-invalidation walkers that didn't know about the 21 new admin.* verbs) → slice validator (25 acceptance commands, 25/25 pass, 1956 vitest tests green) → critic-diff (verdict ship; three non-blocking observations) → scope-judge (`ship_ready: true`; 32/32 acceptance criteria satisfied; acceptance-command parity confirmed).

Test-writer + worker were combined into a single dispatch role for every task this cycle (vs the SKILL's separate-roles default) — a budget-conscious deviation that traded role-isolation for context-economy. The combined role honored the TDD-red-first ordering inside each task; the conductor's loss was the second pair of eyes between test and code. Net: zero retries on any worker; one cross-task respawn (t8) for tests that pre-dated this slice. The combined-role pattern is surfaced in the conductor-loop KB topic for retrospective consideration.

## Decisions

Non-obvious choices made during build, worth pinning:

- **Schema column naming: `member_id → profile_id` for repo-consistency over ADR fidelity.** ADR-0036's §Data model uses `member_id` throughout. The spec at lines 54–81 deviates to `profile_id` to match every other table in this repo that joins against `auth.users` via `profiles` (`audit_log.actor_id`, `privacy_requests.profile_id`, `feature_flags` audit refs, the entire ADR-0035 surface). The deviation is consistently applied across all 7 tables, all 10 RLS policies, the memberships immutability trigger, and the FK declarations. The cost is a one-time ADR-vs-repo divergence; the benefit is every consumer downstream (server actions, RLS contract tests, integration tests) gets to use the established `profile_id` idiom. The scope-judge confirmed the deviation was authorized by the spec.
- **`roleAtLeast` placement: NEW `lib/auth/roleAtLeast.ts` module, NOT an amendment to `lib/auth/types.ts`.** The plan task language ("ADD `roleAtLeast` as a NEW named export to `lib/auth/types.ts`") was the alternative that the authority premortem (R10) flagged as risky — `lib/auth/types.ts` carries a load-bearing JSDoc invariant: "types-only, no runtime payload, no `server-only` directive." Adding a runtime export would either (a) break the invariant by letting `ROLE_RANK` leak to client bundles, or (b) force the `server-only` directive onto a file that every consumer imports types from. T6 took the second option the premortem named: ship as a separate one-function module carrying `import 'server-only';` on line 1. Trade-off: one more module in the auth namespace; benefit: the types-only invariant in `types.ts` remains intact and the runtime function is correctly server-fenced.
- **`target_id = '__stripe_not_configured__'` sentinel (NOT `'pending'`).** Spec AC21.6 was read as recommending `'pending'`; premortem D2 ruled that binding. The reason: `'pending'` collides with the `refund_requests.status='pending'` enum value, breaking forensic queries that try to distinguish denied attempts from in-flight pending refunds. The literal `__stripe_not_configured__` is pinned in three coordinated places: the server action's `withAudit` call site, the `ADMIN_REFUND_DENIED` JSDoc, and the `tests/payments/server-actions-stubs.test.ts` assertion. Future workers replacing the audit sentinel in Slice 2 (when refund_requests rows actually get inserted) need to update all three pins together.
- **sessionStorage-backed idempotency key, NOT `useState(() => crypto.randomUUID())`.** ADR-0005's cashier-redemption pattern names form-mount UUID; the naive implementation is `useState(() => crypto.randomUUID())`. Premortem D3 ruled that binding: StrictMode re-renders and same-tab navigation away-and-back both reset `useState`, producing a different UUID per submission. The fix is `sessionStorage.getItem(\`refund-${targetPaymentId}-${amountCents}\`) ?? crypto.randomUUID()` — keyed by target + amount, persisted across remounts within the same browser tab. The Slice-2 server action will rely on this key staying stable across retries; without the persistence, the unique constraint on `refund_requests.idempotency_key` cannot match the second key and the customer gets double-refunded.
- **Fail-closed RLS in each table's migration (D4) — before the policy migration lands.** Each of migrations 0008..0015 ends with `ENABLE ROW LEVEL SECURITY; ALTER TABLE <table> FORCE ROW LEVEL SECURITY;`. The policy migration 0016 only adds `CREATE POLICY` statements. The default-deny posture is already in place when 0016 runs — any service-role write between table-creation and policy-creation cannot bypass RLS via a missing-policy gap. Each table's shape test asserts the ENABLE+FORCE lines exist in its own migration; the integration test (T20) cross-validates the final composite state.
- **Audit row WRITES BEFORE Stripe-probe THROWS (R1 ordering).** The five-step ordering in `initiateRefund` is load-bearing: requireRole → Zod → assertRefundAuthority → `withAudit` inside `runner.transaction(...)` → `assertStripeConfigured()`. The audit-tx commits BEFORE the Stripe-probe throws. The 25-test suite includes a sequence-tracking mock that pins the exact call ordering `[runner.transaction_called → withAudit_called → withAudit_resolved → runner.transaction_resolved → assertStripeConfigured_called]`. Without the explicit ordering pin, a future "tidy up" refactor that wraps the action body in a try/catch around the Stripe probe would silently revert to "throw first, never audit" — the failure mode would be invisible until forensic analysis tried to count fail-loud encounters.
- **Open Q2 asymmetry — authority-denial does NOT audit; Stripe-not-configured DOES audit.** Premortem R6 explicitly: `InsufficientAuthorityError` throws WITHOUT writing an audit row (intentional per Open Q2 — "user error at the gate"); `StripeNotConfiguredError` writes the `admin.refund.denied` row BEFORE throwing ("system error after the gate"). The asymmetry is documented in a load-bearing comment block above `assertRefundAuthority` in the action. A future ADR amendment could add an `admin.refund.authority_denied` constant + audit emission to eliminate the asymmetry — surfaced for retrospective. The current shape is the deliberate v1 choice (audit log volume tradeoff: spray-attacked refund forms by a compromised manager session would write thousands of authority-denied rows; spray-attacked Stripe-not-configured rows are a much narrower attack surface because the env var rarely flips).
- **GENERATED column for `balance_cents` (Open Q3 resolved toward GENERATED).** The plan named the trigger-update fallback as the safety alternative if pglite rejected the GENERATED expression. T2 ran a throwaway probe at `C:\tmp\conductor36\probe.mjs` against pglite 0.4.5 before writing the production migration: GENERATED works cleanly; direct UPDATE is rejected ("column ... can only be updated to DEFAULT"); math is exact for every seed in `{0, 1, 7, 60, 61, 119, 120, 1234567}` at HOURLY_RATE_CENTS=1200 (no float precision loss). GENERATED variant is structurally immune to the "manual sync drift" failure mode — the trigger-update fallback would have required a separate test that the trigger fires on every UPDATE to `balance_minutes`. The GENERATED variant ships ZERO sync code. The HOURLY_RATE_CENTS literal is pinned in the SQL itself (NOT via a `lib/money` import — premortem R11 — the migration can't depend on application-layer constants), and the shape test asserts the literal `1200` appears verbatim.
- **vitest `testTimeout` 5s → 30s globally.** The wave-5 + wave-6 acceptance commands (RLS contract tests in parallel + integration test applying 16 migrations) hit pglite's parallel-instance memory pressure on Windows; individual tests would time out at 5s under load. The pragmatic single-line change in `vitest.config.ts` is honest about the tradeoff in its JSDoc: 30s is more permissive than ideal but the alternative was per-test `testTimeout` overrides on 7+ files. Long-term fix is `vitest.workspace.ts` projects with isolated timeouts for the pglite-heavy categories; that's a test-infra-cycle follow-up. Critic-diff flagged this as observed-not-blocking.
- **Combined test-writer + worker per task (deviation from SKILL).** The conductor SKILL's default dispatch shape is `test-writer ║ worker → validator` — two separate workers per task, one writing red tests first and the other implementing against them. This cycle combined the two roles into a single dispatch (with the worker honoring the TDD-red-first ordering internally) to economize on context. Net: zero retries across 13 tasks; one cross-task respawn for pre-existing tests outside any worker's scope. The combined-role pattern saved approximately half the worker-context budget at the cost of role-isolation between test design and implementation. Surfaced for retrospective on whether this should become the SKILL default for tightly-scoped substrate slices.

## Notes for future me

- **The premortem-synthesis pattern earned its keep again.** Four premortem dispatches across schema / RLS / authority / fail-loud surfaces produced 44 risks; the synthesis at `.conductor/36/premortem-synthesis.md` distilled six cross-cutting decisions (D1–D6) + per-task pointers + a "what is NOT in this slice" follow-up list. Workers consumed the synthesis on first dispatch and the binding decisions (`auth.role_at_least` namespace, D2 sentinel, D3 sessionStorage, D4 fail-closed-per-table, D5 deny-shape-by-command-type, D6 service-role-positive-sub-case) propagated through every implementation without contract drift. The synthesis-vs-raw-premortems format is the right shape for any slice with 3+ premortem dispatches.
- **`vi.unmock` vs `vi.doUnmock` hoisting trap.** First t12 implementation used `vi.unmock('@/lib/payments/console-availability')` inside the AC30 `it()` block. AC17.1 immediately started failing because **vitest's transformer hoists BOTH `vi.mock` and `vi.unmock` to the top of the file**. The hoisted `vi.unmock` cancelled the file-level `vi.mock(..., () => ({ PAYMENTS_CONSOLE_READY: false }))` for ALL tests in the file, so AC17.1's top-level `openRefundFlow` import suddenly observed the (post-flip) source value `true`. The fix: `vi.doUnmock` (with a `do` prefix) is NOT hoisted and executes at the call site — affects only modules loaded after the call. Inline comment in the test block explains the trap. Document this in the conductor-loop or server-only-and-tests KB; future mock-flip-inverse-assertion blocks will hit the same trap.
- **Prettier wraps `'use server';` directives in parens.** T9's first implementation hit a friction point where Prettier 3 reformats a standalone string-expression-statement at the top of a file by wrapping it in parens — `('use server');` is functionally identical to `'use server';` but Next.js's directive parser is happier with the unwrapped form. The fix: use `// prettier-ignore` immediately above the directive, OR ensure the directive is positioned such that Prettier doesn't have a reason to reformat (e.g., as the literal first non-comment statement with no preceding blank line where Prettier might re-flow). T9 chose the latter. Document the Prettier-vs-Next-directive interaction in the eslint-config KB topic.
- **The 1956-test gauntlet on Windows hit pglite memory pressure in parallel mode.** Wave 5 (`tests/db/rls-*.test.ts`) + the integration test (T20 — 16 migrations applied in sequence) running in parallel under vitest's default parallelism produced sporadic 5s timeouts on individual sub-cases. The 30s global timeout bump is pragmatic but masks the underlying issue (pglite spawns a fresh WASM instance per test file; under parallel load the WASM heap pressure increases tail-latency per query). The right long-term fix is a `vitest.workspace.ts` with the pglite-heavy categories partitioned into a separate project running serially, OR a `tests/db/_fixtures/sharedPglite.ts` that pools instances across files in the same suite. Either is a test-infra-cycle follow-up; the timeout bump unblocks Slice 1.
- **The `member_id → profile_id` repo-consistency deviation is the right call but cost time at spec-writer iter 1.** The ADR text uses `member_id` throughout (because ADR-0010, ADR-0011, and the ADR-0036 §Data model literal block all use `member_id`). Spec-writer iter 1 reproduced the ADR's column names verbatim; critic iter 1 surfaced the gap (every other table in the repo's `supabase/migrations/` tree uses `profile_id`); spec rev 2 pinned the deviation explicitly in §"Schema column naming" so the workers had a single load-bearing reference. Future cycles consuming ADRs whose §Data model literal blocks haven't been updated to match the repo's evolved naming should pre-load this gap into the spec brief — the rule is "repo-consistency wins over ADR fidelity unless the ADR explicitly says otherwise."
- **The combined test-writer+worker dispatch shape worked here.** The SKILL's default is two-worker (test-writer ║ worker → validator); this cycle combined them per task. Zero retries across 13 tasks + 1 cross-task respawn = the combined-role pattern paid for itself in context-budget terms. The risk is real (the test-writer's job is to design the failure mode the worker fixes — collapsing the roles means the worker designs their own failure mode, which is a known cognitive trap), but the substrate-heavy nature of Slice 1 + the four premortem dispatches pre-loading the failure modes externally meant the combined role wasn't blind. The pattern probably doesn't generalize to slices with novel business-logic surfaces; it generalizes well to slices that are mostly substrate + structural contracts.
- **The cross-task respawn is a real role.** T8's first dispatch was clean — 32 audit-action constants + 32 tests + the openRefundFlow amendment + the extractor extension all shipped on first attempt. Wave 4 then landed t9 (`initiateRefund` writing `admin.refund.denied` via the `ADMIN_REFUND_DENIED` constant) and the cross-cutting `tests/admin/audit-event-taxonomy.test.ts` walker started failing because its ADMIN allowed-set was a 17-event hardcoded list that didn't know about ADR-0036's 21 new admin.* verbs. The respawn was a focused 2-file fix (programmatic union of `admin.*`-prefixed constants + path-based exclusion of the fail-loud slice-1 action from the dashboard-cache walker) that took less context than re-dispatching t8. The pattern fits the conductor-loop KB topic: when wave N introduces a verb / constant / module that wave N-1's tests didn't know about, the right shape is a focused cross-task respawn against the affected tests, not a re-run of the original task. Naming the respawn explicitly in the attempts log (`t8.md`) makes the forensic trail clear.
