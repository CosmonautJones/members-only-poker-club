# Audit log

Linked ADR(s): 0006.

The audit_log table is the forensic record-of-record — append-only at the RLS layer (no UPDATE/DELETE policies), written in the same transaction as the change it describes. Cycle 2 landed the table, the policies, the role-change trigger integration, and the `lib/audit/withAudit.ts` TypeScript helper that downstream cycles 3 / 4 / 6 use to wrap server-action mutations.

## Lessons

- **2026-05-10** — `withAudit` follows a caller-owns-the-transaction contract — the helper does NOT manage the transaction itself. *Context:* ADR-0006 cycle 2 t2 attempt 2 — the helper redesign moved `BEGIN`/`COMMIT`/`ROLLBACK` out of the helper. The exported signature is `withAudit<T>(tx, params, mutate)` where `tx` is already a transaction-scoped client. Caller pattern: `await pg.transaction(async (tx) => withAudit(tx, params, mutate))` for tests; `await db.transaction(async (tx) => withAudit(tx, params, mutate))` for production once cycle 3's driver lands. *Why it matters:* This pattern works idiomatically across pglite (`pg.transaction` callback), supabase-js (RPC + transactional pgrst), postgres-js, and `pg`. Helpers that try to manage transactions internally fail under pglite (issuing BEGIN/COMMIT as separate `tx.query()` calls produces autocommit-ish behavior — see pglite KB). The caller-owns-tx pattern also makes the atomicity guarantee transparent — the surrounding `db.transaction()` call is what BEGINs / COMMITs / ROLLBACKs; the helper is just the body. Cycle 3 server actions MUST honor this contract. If a worker calls `withAudit(params, mutate)` without the surrounding transaction, atomicity silently breaks.
- **2026-05-10** — The one-transaction invariant is load-bearing — the helper does NOT catch any throw. *Context:* ADR-0006 cycle 2 AC6 / AC9.3 — the keystone safety property is "a mutation cannot commit without its audit row." The required ordering inside the caller's single tx is `mutate(tx) -> tx.query('INSERT INTO audit_log ...') -> caller's COMMIT`. If `mutate` throws OR the audit INSERT throws, the helper propagates without catching; the surrounding `pg.transaction(...)` (or driver equivalent) ROLLBACKs. *Why it matters:* Three forbidden implementations are explicitly called out in the helper's JSDoc — (a) two separate transactions for mutate vs audit, (b) try/catch around the audit INSERT that swallows the error and commits the mutation anyway, (c) any best-effort / fire-and-forget audit pattern. A worker who refactors for "cleanliness" by adding any of these silently breaks the audit log's anti-state-without-history posture. The only try/catch inside the helper is around `JSON.stringify(before/after)` — a pre-call serializability check that converts BigInt / circular-ref to a clear TypeError BEFORE the audit INSERT runs. AC9.3 simulates audit-INSERT failure via a contrived CHECK constraint (`audit_log_test_action_nonempty CHECK (action <> '__force_fail__')`) to prove the helper rolls back the mutation when the audit INSERT itself fails.
- **2026-05-10** — `auth.uid() IS NOT NULL` in the INSERT WITH CHECK clause intentionally denies anon — service-role inserts succeed via Postgres-role BYPASSRLS, NOT via policy weakening. *Context:* ADR-0006 cycle 2 AC4 INSERT-policy contract — the `audit_log_insert_authenticated` policy is `WITH CHECK (auth.uid() IS NOT NULL)`. System-level / service-role inserts (Stripe webhook handlers, admin scripts, the role-change trigger run as superuser) succeed because their Postgres role has the BYPASSRLS attribute — the policy never evaluates for those callers. *Why it matters:* Three drift patterns are explicitly forbidden by the migration's comment block AND by AC8 regex/AST shape tests: relaxing to `WITH CHECK (true)`, adding a second permissive policy, OR adding an `OR auth.uid() IS NULL` disjunct. Any of these would let anon inject forged audit rows and break the audit log's anti-forgery posture. The apparent tension between the policy's `IS NOT NULL` predicate and the test cases that assert NULL-actor INSERTs succeed is resolved at the Postgres-role layer (BYPASSRLS), NOT the policy layer. A worker who "fixes" the apparent contradiction by weakening the policy has broken the contract.
- **2026-05-10** — The audit_log table's append-only invariant is enforced at the RLS layer (no UPDATE / DELETE policies); service-role bypass is an acknowledged escape hatch, NOT a normal-path operation. *Context:* ADR-0006 cycle 2 AC7.9 — RESET ROLE + clear `test.uid` lets service-role SELECT/INSERT/UPDATE/DELETE on audit_log (BYPASSRLS at the Postgres-role level). This is the legitimate webhook-handler / admin-script path per ADR-0006. *Why it matters:* Production policy is "service-role does NOT UPDATE/DELETE audit_log" — enforced by code review and (per ADR-0006) by an `audit-policy` ESLint rule that ships in Slice 4. Cycle 2 does NOT implement the lint. The RLS posture is necessary but not sufficient; the lint is the application-level guard. Until then, any cycle that adds a service-role-context audit-log mutation MUST have a critic flag for "this is the documented escape hatch, NOT a normal path" — UPDATE/DELETE on audit_log is reserved for emergency manual repair only.
- **2026-05-10** — The role-change trigger is extended via `CREATE OR REPLACE FUNCTION`; the trigger declaration itself is NOT re-issued in cycle 2's migration. *Context:* ADR-0006 cycle 2 AC5 — `0003_audit_log.sql` only replaces the function body; the `CREATE TRIGGER profiles_protect_role_change` declaration stays in cycle 1's `0002_profiles_and_roles.sql`. *Why it matters:* Re-issuing the trigger declaration would risk dropping the column-mention semantics (`BEFORE UPDATE OF role`) or inverting the alphabetical firing order vs `set_updated_at`. The shape test asserts NO `CreateTrigStmt` for that name in `0003_audit_log.sql`, AND AC7.13 introspects `pg_trigger` post-migration to confirm `profiles_protect_role_change` still sorts before `set_updated_at` on `public.profiles`. A worker who "helpfully" rewrites the trigger declaration in a future cycle can silently break both invariants — keep the function-body-only modification pattern.
- **2026-05-15** — Role changes emit TWO audit rows by design — the DB trigger AND the server action both write. *Context:* ADR-0035 t13 `changeRole` server action wraps the role mutation in `withAudit('admin.member.role_changed', ...)` which writes one row. The cycle-1 trigger `profiles_protect_role_change` ALSO writes a `profile.role_change` row in the same transaction (cycle 2's extension to the trigger function). Both rows commit or both roll back. Premortem R3 for ADR-0035 surfaced the failure mode: a future migration that consolidates triggers could silently omit the trigger emission, dropping back to one row, and no test would catch it because `audit_log` would still grow. The defense is `tests/admin/role-ladder-defense.test.ts` — asserts EXACTLY 2 rows for the target_id within a 1-second window after a `changeRole` mutation, AND `tests/migrations/role-change-trigger-shape.test.ts` regexes the latest migration touching `profiles_protect_role_change` for the `INSERT INTO audit_log` literal in the function body. *Why it matters:* The two-row pattern looks redundant at first glance — a worker "tidying up" the server action by removing the `withAudit` wrapper would still leave one row from the trigger, and the action would still complete. But the two rows carry different forensic axes: the trigger row is the DB-level "role column actually changed" record; the action row is the application-level "manager X invoked changeRole against profile Y for reason Z." The application row carries actor_role + outcome metadata the trigger can't see. Removing either side silently breaks the forensic invariant. The count assertion is load-bearing.
- **2026-05-15** — Custom error classes used inside `withAudit` mutate callbacks MUST extend `Error` AND set `this.name`. *Context:* ADR-0035 premortem R12 — a worker who `throw 'SelfEditViolation'` (string, not Error) inside a `withAudit` callback risks the helper's JSON-serializability check at the audit-INSERT boundary, plus breaks the analytics `classifyAdminActionError` mapping which reads `error.name`. The fix is `tests/admin/withAudit-throw-discipline.test.ts` — walks every action file under `app/(admin)/admin/**/_actions/*.ts` and asserts (1) no `throw 'string'` form is used, (2) every exported class in `_errors.ts` `extends Error`, (3) every class sets `this.name = '<ClassName>'` in its constructor. *Why it matters:* The `withAudit` helper does NOT catch any throw (cycle 2 KB lesson, 2026-05-10) — it propagates and the surrounding `tx.transaction(...)` rolls back. Non-Error throws still trigger the rollback, BUT: (a) Sentry / PostHog `classifyAdminActionError(error.name)` returns `'unknown'` instead of the meaningful tag; (b) the JSON-serializability check in `withAudit` may produce a different shape than the developer expected. Discipline costs nothing and removes both failure modes. New error classes in this repo MUST follow the pattern documented in `app/(admin)/admin/_errors.ts` — seven classes there are the canonical reference.
- **2026-05-10** — `actor_id` FK to `auth.users(id)` MUST NOT be `ON DELETE CASCADE` — ADR-0023's anonymization model replaces the actor record with a `del:<hash>` token but the audit row itself is NEVER deleted. *Context:* ADR-0006 cycle 2 t1 + AC8 AST tier — the migration ships with implicit `NO ACTION` (the Postgres default) on the FK; the shape test asserts no `CASCADE` / `SET NULL` ON DELETE clause in the AST. *Why it matters:* If a future migration "tidies up" by adding `ON DELETE CASCADE`, deleting an `auth.users` row would silently delete every audit row referencing it — a privacy law violation (the audit log is forever-retained per ADR-0006; ADR-0023 anonymizes the actor reference, not the action history). Cycle 6 (ADR-0023) MAY change the FK to `ON DELETE SET NULL` when it implements anonymization, but cycle 2's posture is "implicit NO ACTION" and the shape test guards against drift.
