# Money handling

Linked ADR(s): 0004.

## Lessons

- **2026-05-16** — `payments.currency` carries BOTH a column DEFAULT `'usd'` AND a row-level `CHECK (currency = 'usd')` constraint — belt-and-suspenders for the USD-only ADR-0004 invariant; the `CHECK` is the load-bearing enforcement and the shape test negative-asserts no `IN (...)` form. *Context:* ADR-0036 Slice 1 t1 + premortem R1 — the payments migration ships `payments_currency_usd_only CHECK (currency = 'usd')` even though the column default already pins the value. *Why it matters:* a future migration "tidying up" the constraint to `CHECK (currency IN ('usd', 'eur', ...))` would silently widen the invariant; the shape test grep for `IN (` on the currency column will fail loudly. ADR-0004 USD-only is structural, not a default. Migrating off USD-only requires an ADR amendment, NOT a constraint relaxation. Same posture applies to any future single-value-allowed columns where the constraint is the contract.

- **2026-05-16** — `time_wallets.balance_cents` is a `GENERATED ALWAYS AS ... STORED` column with the `HOURLY_RATE_CENTS=1200` literal pinned in the SQL itself (NOT imported from `lib/money/types.ts`) — Postgres rejects direct UPDATEs with "column ... can only be updated to DEFAULT" so manual sync drift is structurally impossible. *Context:* ADR-0036 Slice 1 t2 + Open Q3 — pglite 0.4.5 was probe-tested to confirm acceptance before committing the choice; the trigger-update fallback (`BEFORE INSERT OR UPDATE` keeping `balance_cents = round(balance_minutes/60.0 * 1200)` in sync) was the safety alternative the plan named, NOT shipped. *Why it matters:* the migration cannot depend on application-layer constants (premortem R11). Pinning `1200` in the SQL means a future change to `HOURLY_RATE_CENTS` requires a coordinated migration + lib edit + shape-test update — visible in code review, NOT a silent drift. The shape test seeds `balance_minutes ∈ {0, 1, 7, 60, 61, 119, 120, 1234567}` and asserts `balance_cents = balance_minutes * 20` exactly at rate=1200 (no float precision loss). Same posture applies to any future GENERATED columns: rate literals live in SQL, sync via the generated expression, NOT a trigger.
