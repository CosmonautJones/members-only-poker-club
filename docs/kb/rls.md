# Row-Level Security

Linked ADR(s): 0003.

## Lessons

- **2026-05-09** — `FORCE ROW LEVEL SECURITY` is defense-in-depth, not a fix for `BYPASSRLS`. *Context:* ADR-0003 cycle 1 — added FORCE to the `profiles` migration after pglite tests bypassed RLS, but 11 sub-tests still failed because pglite's default user has the `BYPASSRLS` user-attribute, which short-circuits policy evaluation BEFORE FORCE is consulted. *Why it matters:* FORCE only applies RLS to table-OWNER connections; BYPASSRLS lives on the role itself and is checked first. To genuinely test RLS in a substrate that connects as a superuser by default (pglite, fresh Postgres), you must `CREATE ROLE … NOBYPASSRLS` and `SET ROLE` — FORCE alone won't save you. In production Supabase the anon/authenticated roles are NOT superuser and never own tables, so FORCE is a no-op there but is still worth shipping for posture.
- **2026-05-09** — Test RLS via a `SET ROLE` to a non-superuser role that mirrors Supabase's `authenticated`. *Context:* ADR-0003 cycle 1 — RLS suite at `tests/db/rls-profiles.test.ts` does `CREATE ROLE app_authenticated NOBYPASSRLS NOINHERIT` + GRANTs in `beforeAll`, then `SET ROLE` for the per-test connection. For service-role bypass tests, `RESET ROLE` to switch back to superuser. *Why it matters:* This is a dual-axis model — the Postgres role controls BYPASSRLS, the `auth.uid()` GUC controls policy predicates. Future cycles testing RLS on other tables (audit_log in cycle 2, ID verification in cycle 4) reuse this `asAuthenticated()` / `asServiceRole()` / `withRollback()` helper shape. Lift the helpers into a shared `tests/db/_fixtures/rls-helpers.ts` once the second cycle reaches for them.
- **2026-05-09** — Assert on SQLSTATE codes, never on EXCEPTION message text. *Context:* ADR-0003 cycle 1 — every `rejects.toMatchObject` call in the RLS and protect-trigger tests uses `{ code: '42501' }` only. The migration's RAISE EXCEPTION message string `'role change requires manager+'` does not appear in any test. *Why it matters:* Insulates the suite from copy edits to the message and from future error-message localization. Also pin `expect.assertions(N)` on every rejection-branch test so the test fails loudly if the rejection branch never runs (otherwise `await expect(badThing()).rejects.toMatchObject(...)` silently passes when `badThing()` resolves).
- **2026-05-09** — Test column-targeted triggers with three privilege-escalation variants. *Context:* ADR-0003 cycle 1 AC8.10 — own-row role-update rejection has variant A (simple `SET role = …`), variant B (multi-column `SET role = …, full_name = …`), and variant C (no-op `SET role = role`). *Why it matters:* `BEFORE UPDATE OF role` triggers fire whenever the column appears in the SET clause, even if the new value equals the old. Variant C catches a class of subtle drift if a future migration switches the trigger to "value actually changed" semantics; variants A and B alone would still pass.
- **2026-05-15** — When a table predates an RLS policy, fix-forward with a new migration — DO NOT rewrite the original. *Context:* ADR-0035 t1 — `feature_flags` shipped in cycle 1's `0001_feature_flags.sql` without RLS (deliberately, to unblock cycle-1 readers before role plumbing existed). Cycle 4 needed RLS to land before the admin flag-toggle action. T1 added `0006_feature_flags_rls.sql` with `ALTER TABLE feature_flags ENABLE ROW LEVEL SECURITY; FORCE ROW LEVEL SECURITY;` + the two new policies, AND amended `COMMENT ON TABLE feature_flags` forward to reflect the new posture. Cycle-1's migration was NOT edited (per ADR-0018 immutability). *Why it matters:* Editing a shipped migration breaks every downstream migrate:check + every dev's local pglite state, and creates a hash-mismatch surface that's painful to diagnose. The fix-forward pattern is the same as cycle 2's `0003_audit_log.sql` extending cycle 1's trigger via `CREATE OR REPLACE FUNCTION` — the original schema-defining migration is immutable; subsequent migrations layer on top. The reasoning that would normally go in the original file's header comment goes into the new migration's top-of-file comment block plus the `COMMENT ON TABLE` amendment.
- **2026-05-15** — When the spec asserts "RLS-denied UPDATE raises 42501" and you've already read the 2026-05-10 lesson, push back during the critic phase. *Context:* ADR-0035 AC2 (cycle 4) prose said "A `member`-roled session UPDATE against `feature_flags` raises SQLSTATE `42501`." This is the SAME error cycle 2 already pinned in this KB on 2026-05-10. Worker t1 honored observed Postgres behavior (rowCount=0) in the test, shipped, and flagged the spec divergence in the dispatch — correct outcome but the cycle could have skipped the divergence flag if the spec-writer had pre-loaded the 2026-05-10 lesson. *Why it matters:* The 42501-vs-rowCount=0 distinction depends on the policy SHAPE (separate UPDATE policy with permissive USING + restrictive WITH CHECK raises 42501 on commit; FOR ALL with restrictive USING returns rowCount=0 silently). When a spec prescribes a FOR ALL write policy AND asserts 42501 on member UPDATE, the assertions contradict each other. Spec-writer agents in future cycles touching RLS UPDATE/DELETE assertions MUST read this topic and refuse to ship a spec that prescribes both at once. Either change the policy shape or change the assertion.
- **2026-05-10** — RLS-denied UPDATE / DELETE returns `affectedRows: 0` SILENTLY, NOT SQLSTATE 42501. *Context:* ADR-0006 cycle 2 AC7.7 / AC7.8 — under `app_authenticated NOBYPASSRLS NOINHERIT` with FORCE RLS + GRANT UPDATE/DELETE ON audit_log + NO `FOR UPDATE` / `FOR DELETE` policy, attempts to `UPDATE audit_log SET action='forged' WHERE id=$1` resolved with `affectedRows: 0` instead of rejecting with 42501. The first-attempt assertion `rejects.toMatchObject({ code: '42501' })` was wrong about PG semantics. *Why it matters:* PG only raises 42501 for missing GRANTs at the table-level OR explicit `RAISE EXCEPTION USING ERRCODE = '42501'` from a trigger / function. With grants present and no policy permitting the operation, the row is invisible (USING evaluates implicit-false), the statement matches 0 rows, and it returns silently. The append-only invariant is "no row state changed", proven by the dual assertion `expect(updateRes.affectedRows).toBe(0)` PLUS `RESET ROLE` + service-role read confirms the row state did NOT change. This is more correct PG semantics than "always assert 42501 on RLS denial" — adapt the assertion to whichever invariant the policy posture actually enforces.
