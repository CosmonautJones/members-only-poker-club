# Idempotency & exactly-once

Linked ADR(s): 0005.

## Lessons

- **2026-05-16** — Form-mount idempotency-key UUIDs MUST be persisted via `sessionStorage` keyed by the target operation parameters, NOT via `useState(() => crypto.randomUUID())`. *Context:* ADR-0036 Slice 1 t11 + premortem D3 — the refund-initiation form's `IdempotencyKeyField.client.tsx` reads `sessionStorage.getItem(\`refund-${targetPaymentId}-${amountCents}\`) ?? crypto.randomUUID()` so the key survives StrictMode remount + same-tab navigation away-and-back. *Why it matters:* a fresh UUID per submission breaks the server-side unique-constraint dedup — the customer gets double-refunded because two distinct keys both pass `INSERT INTO refund_requests`. `useState(() => initializer)` is the naive pattern that ADR-0005's prose names as form-mount; `useState` is reset on remount and the initializer fires again. The fix is to persist the minted value at the browser-tab scope so retries of the same submission carry the same key. The empty initial-render value + post-mount `useEffect` write prevents the SSR-vs-CSR hydration-mismatch from the non-deterministic UUID source. Apply this pattern to every form whose submission carries an idempotency contract.

- **2026-05-16** — Duplicate-`idempotency_key` INSERT raises SQLSTATE `23505` exactly — pin the literal in shape tests so handler code can pattern-match. *Context:* ADR-0036 Slice 1 t3 — the `refund_requests` and `time_ledger` shape tests both seed a duplicate idempotency_key INSERT and assert `caught.code === '23505'` (NOT just "any error"); Slice 2's handler will catch this code specifically to recover (return the existing row instead of re-attempting). *Why it matters:* a worker who refactors a UNIQUE constraint to a partial-UNIQUE WHERE clause OR removes the constraint entirely + relies on application-layer dedup silently breaks the handler's recovery path — and the SQLSTATE assertion in the shape test fails loudly. The 23505-vs-23514-vs-42501 distinction is the contract between the schema layer and the handler layer; pin the SQLSTATE in tests, not just "an error was raised".
