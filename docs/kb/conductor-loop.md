# Conductor loop — spec fidelity, critic-diff, revise iters

Linked ADR(s): the conductor harness itself (Slice 1 infra), plus every ADR run through it. Lessons here are about the conductor's structural contract — when validator-PASS isn't enough, when critic-diff earns its keep, how the revise budget reads.

## Lessons

- **2026-05-10** — The spec's touched-files inventory is load-bearing — every `Create: <path>` line MUST land as a separate module, even when the AC behavior could be satisfied by inlining. *Context:* ADR-0002 cycle 3 revise iter 1 — the worker satisfied every numbered AC behaviorally; slice validator returned PASS (587 tests green, lint clean, typecheck clean). Critic-diff iter 1 then flagged 5 of 7 concerns as "the spec lists `Create: lib/auth/types.ts` (and `safeNext.ts`, and `errors.ts` server-only directive, and `app/(auth)/layout.tsx`) as touched-files inventory items; the worker inlined those into call-site files because the AC's behavior worked either way." Cycle 4's planner would have hit `import { Profile } from '@/lib/auth/types'` and failed with no signal pointing back to the cycle-3 worker. *Why it matters:* The validator catches "tests pass / types check / lint clean" but cannot see forward-compat structure — a future cycle's import-by-path expectation. The structural-fidelity check is what the critic-diff exists for, but pre-loading the lesson into the worker brief saves a revise-loop round trip. The rule for future workers: when the spec writes `Create: <path>`, that file MUST exist as a standalone module, even if no current caller would notice.
- **2026-05-10** — The critic-diff iter-1 → iter-2 loop is the right cost — accept it; don't try to skip it. *Context:* ADR-0002 cycle 3 — slice validator returned PASS; critic-diff iter-1 returned `revise` with 7 concerns; revise worker iter fixed the 7 concerns; two cascading test-infra revises (lint cast in iter 2; transitive `server-only` + JSDoc-substring trap in iter 3); slice validator iter-3 returned PASS again; critic-diff iter-2 returned `ship`; scope-judge returned `ship_ready: true`. Three worker iters total within the 5-iter conductor budget. *Why it matters:* The validator-PASS-then-critic-revise pattern is NOT redundant work — it's the mechanism that catches "ACs pass but spec structure missed." Cycle 1 (ADR-0003) and cycle 2 (ADR-0006) didn't need the revise loop because their slices were schema-only; the structural surface was the migration file itself, and the validator's shape tests caught it directly. Cycle 3 (ADR-0002) was the first multi-module surface (8+ files across `lib/auth/`, `app/(auth)/`, `app/(member)/`, `middleware.ts`) where structural intent and AC behavior could plausibly diverge. Future cycles with multi-module surfaces should plan on the revise loop firing at least once — budget for it, don't treat it as a defect.
- **2026-05-10** — When revise iter N introduces a new module-level invariant (e.g. `import 'server-only';`, or a new shared dep), it WILL cascade test-infra failures in iter N+1. *Context:* ADR-0002 cycle 3 revise iter 1 added `import 'server-only';` to `lib/auth/safeNext.ts` and added a JSDoc explaining the absence of `'use client'` on `auth-layout.tsx`. Validator iter 2 failed at lint (a previously-acceptable type cast became unnecessary because the type inference tightened); validator iter 3 failed at module-load time in `login-action.test.ts` (transitive `server-only` import) AND at a substring assertion in `auth-layout.test.ts` (`'use client'` literal in JSDoc). Three revise iters total. *Why it matters:* The pattern is predictable — new directive → new module-load failure modes; new shared module → new lint/type artifacts; new comment → new substring-test false positives. The cleanest path is to bundle the structural fix and the consequent test-infra fix in the same revise dispatch. The workers don't fail at this because they fix what they're asked to fix; the dispatch brief is what should pre-load the cascade. If a revise dispatch adds an `import 'server-only';` to any module, the same dispatch should grep callers and pre-emptively add `vi.mock('server-only', () => ({}))` to every test file that imports the chain.
- **2026-05-10** — Three worker iters fits comfortably in the 5-iter conductor budget; 4+ iters is a re-spec signal. *Context:* ADR-0002 cycle 3 ran 3 worker iters (initial build → revise iter 1 for 7 critic concerns → revise iter 2 for lint cast → revise iter 3 for test infra). All within the 5-iter budget. *Why it matters:* The budget exists for a reason; this cycle didn't need to spend it. Future cycles whose revise loop exceeds 3 iters are surfacing a structural gap in the spec or the plan, NOT a sloppy worker. The triage rule: 4+ iters → pause the conductor, re-spec the gap, re-plan, restart. Don't keep grinding revise iters past 3 — the marginal cost of context decay (each revise iter loads more `attempts/` history) outweighs the marginal benefit. Cycle 3's 3-iter run is the new high-water-mark expectation for multi-module surfaces.

- **2026-05-16** — `vi.unmock(...)` is HOISTED by vitest's transformer like `vi.mock(...)` — it cancels the file-level mock for ALL tests in the file. Use `vi.doUnmock(...)` (with the `do` prefix) for non-hoisted call-site unmocking inside an `it()` block. *Context:* ADR-0036 Slice 1 t12 — the AC30 inverse-assertion block needed to dynamically import the action with the REAL `PAYMENTS_CONSOLE_READY` value (true post-flip) while preserving the file-level `vi.mock('@/lib/payments/console-availability', () => ({ PAYMENTS_CONSOLE_READY: false }))` for every OTHER test in the file. First implementation used `vi.unmock` inside the `it()` body — AC17.1 (running BEFORE the new block) immediately started failing because the hoisted `vi.unmock` cancelled the file-level mock at module-load time, so AC17.1's top-level `openRefundFlow` import observed the post-flip `true` value. Fix: `vi.doUnmock` + `vi.resetModules()` + dynamic re-import inside the `it()` body, with a belt-and-braces `vi.doMock(..., () => ({ PAYMENTS_CONSOLE_READY: false }))` at the end of the block to restore the override for any subsequent test that does its own dynamic import. *Why it matters:* this trap is invisible at write-time — the test reads correctly and the unmock seems scoped to the block. The failure mode (sibling tests in the same file silently observing the un-mocked value) is the kind of test-pollution that produces flaky CI three commits later. Document at every mock-flip-inverse-assertion site: inline comment naming the hoisting trap + the `vi.doUnmock` choice.

- **2026-05-16** — Prettier 3 wraps standalone string-expression statements (like `'use server';`) in parens — file-positioning matters or use `// prettier-ignore`. *Context:* ADR-0036 Slice 1 t9 — Prettier's first pass over `initiateRefund.ts` reformatted the `'use server';` directive to `('use server');` which Next.js's directive parser does NOT recognize as a Server Actions opt-in. Fix: position the directive as the literal first non-comment statement with no preceding blank line where Prettier might re-flow, OR add `// prettier-ignore` immediately above. T9 chose the former. *Why it matters:* the failure is silent at lint-time (Prettier accepts both forms; ESLint doesn't catch the semantic regression) and surfaces as a runtime "Server Actions cannot be called from..." error or as the action silently becoming a client-side function. Pair this with the cross-cutting `import 'server-only';` directive: both directives are formatting-sensitive. Test invariant: source-grep for the exact unwrapped literal `'use server';` (without surrounding parens) on its own line.

- **2026-05-16** — Cross-task respawn is a real role — when wave N introduces a verb/constant/module that wave N-1's tests didn't know about, focused 2-file fix beats re-dispatching the original task. *Context:* ADR-0036 Slice 1 — t8 shipped 22 audit-action constants cleanly on first attempt; wave 4 then landed t9 writing `admin.refund.denied` via `ADMIN_REFUND_DENIED`. Two pre-existing cross-cutting tests (`tests/admin/audit-event-taxonomy.test.ts` with a hardcoded 17-event allowed-set; `tests/admin/dashboard-cache-invalidation.test.ts` with a "every mutation-class action calls revalidateTag" walker) immediately failed because they didn't know about the 21 new admin.* verbs OR the fail-loud-no-mutation posture of `initiateRefund`. The respawn (`.conductor/36/attempts/t8.md`) was a focused 2-file fix: programmatic union of `admin.*`-prefixed constants in the taxonomy test + path-based `FAIL_LOUD_PATH_EXCLUSIONS` in the cache-invalidation walker. *Why it matters:* the respawn took less context than re-dispatching t8 with an extended scope (t8's success was tightly bound to its constraint list; widening would have invalidated the whole worker brief). Name the respawn explicitly in `attempts/<task>.md` so the forensic trail is clear; the dispatch envelope for the respawn should reference the failing test file path + the exact failure mode + the fix shape (path-based exclusion vs heuristic exclusion vs allowed-set extension), NOT re-derive from scratch.

- **2026-05-16** — Combined test-writer + worker dispatch (deviation from SKILL default) works for substrate slices with strong premortem pre-loading — but is risky for novel-business-logic slices. *Context:* ADR-0036 Slice 1 — every task this cycle combined the SKILL's separate test-writer + worker roles into a single dispatch (with the worker honoring TDD-red-first internally). Zero retries across 13 tasks; one cross-task respawn. Saved roughly half the worker-context budget. *Why it matters:* the risk is real — the test-writer's job is to design the failure mode the worker fixes; collapsing the roles means the worker designs their own failure mode, a known cognitive trap. Slice 1's substrate-heavy nature + four premortem dispatches pre-loading failure modes externally meant the combined role wasn't blind — the premortem WAS the test-writer's externalized contribution. The pattern probably doesn't generalize to slices with novel business-logic surfaces (where failure modes aren't pre-enumerable from prior cycles). Surfaced for retrospective on whether substrate slices should default to combined-role + premortem-heavy, while business-logic slices keep the separate-role default.

- **2026-05-17** — Conductor v0.5 bundles three coordinated fixes (Goal Integration, turn-boundary discipline, learning loop) plus the first manual application of `/conductor learn` — applying ADR-0035 retrospective Diffs 1, 2, 4 to SKILL.md and templates. *Context:* user-driven self-improvement pass on the conductor skill. ADR-0035's retrospective produced 5 structured `proposed_diffs` (3 strong, 1 medium, 1 discipline) on 2026-05-15 but they sat unconsumed because no merger existed. v0.5 ships the `/conductor learn` sub-command AND closes the seam by applying the high-leverage diffs (finisher fold-in, mid-flight worker failure recovery, RLS contract authoring) bundled with the same patch that introduces the merger — bootstrap-the-bootstrap pattern. *Why it matters:* prior 12+ cycles produced friction data that never reached the SKILL.md source. The bottleneck was not the proposals (those were rich and structured) but the apply step. By making `proposed_diffs[]` a required field on `RetrospectiveResultSchema` and giving the merger a single command, every future cycle's lessons can roll into the skill on user-confirm. The 60s vs 1200s ScheduleWakeup distinction is load-bearing: tight retry loops stay in cache (60s < 5min TTL); ratification waits accept the cache miss (1200s, one miss buys 20+ minutes). Future cycles whose `/conductor learn` review shows 5+ proposed_diffs from the same run should consider bundling them into a SKILL minor-version bump rather than applying piecemeal — the v0.5 bundle of three coordinated diffs proved the pattern.

- **2026-05-17** — `/goal` + `/conductor` need a sentinel contract (per-turn parseable terminator) because the `/goal` Haiku evaluator runs BETWEEN turns. *Context:* user reported `/goal + /conductor` causing "major waiting/exit-block loops that may be wasting tokens." Audit found three root causes: (1) conductor never emitted `GOAL-A:` / `PING:` / `GOAL-C:` sentinels, so /goal couldn't detect completion/block/yield; (2) sync wait-loops inside a single turn (validator max-5 retries, critic max-3 revises, ratifier max-3 revises) ballooned the turn's context AND were invisible to /goal's per-turn evaluator; (3) the existing prescription "background-dispatch + ScheduleWakeup" (SKILL.md token-efficiency rules 5 + 10) was a directive without an implementation pattern, so the orchestrator defaulted to sync. *Why it matters:* v0.5 codifies turn-boundary discipline — each retry iteration is its own turn (dispatch → emit `GOAL-C:` → ScheduleWakeup → end turn → resume). The orchestrator NEVER runs a `while` loop inside a turn. This compounds with the cache-TTL fact: a 60s wakeup keeps cache warm; a sync 5-iter loop blows the prompt-cache budget AND hides progress from /goal. The canonical reference is `docs/kb/conductor-goal-integration.md`. Future skills that compose under /goal MUST surface state via transcript sentinels — not via filesystem signals or escalation-prose blobs.
