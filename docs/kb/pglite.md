# pglite (in-process WASM Postgres)

Linked ADR(s): 0003 (test substrate for RLS); 0006, 0009 (downstream cycles will reuse the harness).

We use `@electric-sql/pglite` as the test substrate for migration + RLS suites because the conductor host has no Docker daemon and the npm-installable WASM build is real Postgres 16. Trade-off: pglite does not bundle Supabase's `auth` schema, ships a reduced contrib-extensions catalog, and connects as a superuser-owner by default. The harness paves over each of these explicitly.

## Lessons

- **2026-05-09** — Don't `CREATE EXTENSION IF NOT EXISTS pgcrypto` in pglite — the extension isn't bundled, and `IF NOT EXISTS` does NOT suppress "extension not available" errors. *Context:* ADR-0003 cycle 1 t4 attempt 1 — the auth-stub setup tried to install pgcrypto for `gen_random_uuid()` and pglite raised `extension "pgcrypto" is not available` before any test block ran. *Why it matters:* `gen_random_uuid()` has been in core Postgres (pg_catalog) since 13, and pglite is built on Postgres 16 — it ships natively. `IF NOT EXISTS` only short-circuits the "extension already installed" case, not the "extension doesn't exist on this server" case. Drop the `CREATE EXTENSION` line entirely; if you need a UUID in test code, use Node's `crypto.randomUUID()` and pass it as a parameterized INSERT value.
- **2026-05-09** — pglite's default user is a superuser-owner with `BYPASSRLS` — RLS is silently bypassed unless the harness creates a non-superuser role and `SET ROLE`s to it. *Context:* ADR-0003 cycle 1 t4 attempt 2 — after dropping pgcrypto, all 43 sub-tests collected, but 11 RLS-gated operations succeeded when they should have been denied. Root cause: pglite connects as `postgres` (superuser, BYPASSRLS, table owner). `ENABLE ROW LEVEL SECURITY` and even `FORCE ROW LEVEL SECURITY` cannot override the BYPASSRLS user-attribute — it's checked first and short-circuits all policy evaluation. *Why it matters:* This is the dominant pglite gotcha for any RLS work. The fix pattern: `CREATE ROLE app_authenticated NOBYPASSRLS NOINHERIT` + `GRANT USAGE ON SCHEMA …` + `GRANT SELECT/INSERT/UPDATE/DELETE ON <table>` + `GRANT EXECUTE ON FUNCTION …` + `SET ROLE app_authenticated`. Mirrors Supabase's production role architecture (`anon`, `authenticated`, `service_role` are all NOT superuser). For service-role bypass tests, `RESET ROLE` back to superuser temporarily.
- **2026-05-09** — Seed fixtures BEFORE the `SET ROLE` switch — seeds run as superuser (mirroring production seeds-via-service-role); per-test queries run as the limited role. *Context:* ADR-0003 cycle 1 — the `beforeAll` seeds `auth.users` and `profiles` rows while still connected as superuser, then runs `SET ROLE app_authenticated` for the per-test connection. *Why it matters:* Production Supabase seeds via the service-role key, which has BYPASSRLS, so seed-time RLS-bypass is the correct semantic. If you `SET ROLE` before seeding, the seeds themselves get rejected by the very policies you're testing. Order matters: migration → role creation + grants → seeds → SET ROLE.
- **2026-05-09** — Use `pg.exec(sql)` for migrations / DDL batches; use `pg.query(sql, params)` for parameterized statements only. *Context:* ADR-0003 cycle 1 — the migration is a multi-statement batch (CREATE TYPE, CREATE TABLE, multiple CREATE POLICY, multiple CREATE TRIGGER). `pg.query()` rejects multi-statement input with a parse error; `pg.exec()` accepts it. *Why it matters:* This is a pglite-specific API split that other Postgres clients (`pg`, `postgres.js`) don't enforce — workers used to other drivers will reach for `pg.query()` first.
- **2026-05-09** — pglite's `transaction()` auto-commits on success. Use a manual `BEGIN` / `ROLLBACK` pair for test isolation. *Context:* ADR-0003 cycle 1 — the RLS suite has a `withRollback(body)` helper that does `BEGIN` + body + `ROLLBACK` instead of `pg.transaction(body)`. *Why it matters:* The shared pglite session is reused across sub-tests; if a mutating test commits, state leaks into the next test. The manual ROLLBACK guarantees no state escapes regardless of whether the body resolves or throws.
- **2026-05-09** — Run smoke-test invariants in the auth-stub setup, not just at first-test-run. *Context:* ADR-0003 cycle 1 — `setupAuthStub(pg)` checks four invariants (GUC session-scoping, NULL-on-clear, default 'authenticated' role, return-type signature) before returning. *Why it matters:* If pglite's GUC scoping or function-resolution model regresses in a future version (or if a worker swaps in a different Postgres-in-WASM build), the setup throws with a pointed error message instead of letting downstream RLS tests pass under a silently-broken stub. Cheap insurance against substrate drift.
- **2026-05-10** — `pg.query('BEGIN')` + `pg.query('COMMIT')` is NOT a real transaction in pglite. Use the `pg.transaction(async (tx) => ...)` callback API instead. *Context:* ADR-0006 cycle 2 t2 attempt 1 — `withAudit` opened its own transaction by issuing `tx.query('BEGIN')`, running the mutation + audit INSERT, then `tx.query('COMMIT')` (or relying on the throw-and-rollback flow). t6 attempt 2 surfaced 10 cascading failures and confirmed neither commit nor rollback actually transacted: a "rolled-back" mutation persisted into the next test, and the connection ended up in `current transaction is aborted, commands ignored until end of transaction block` state. *Why it matters:* pglite's idiomatic transaction API is the callback form — `pg.transaction(async (tx) => ...)` BEGINs, runs the callback, COMMITs on resolve, ROLLBACKs on reject, and provides a tx-scoped client. Issuing BEGIN/COMMIT/ROLLBACK as separate `pg.query()` calls produces autocommit-ish behavior that does NOT roll back on throw. The durable design pattern: helpers that need atomicity should NOT manage transactions internally — make the helper assume it is already inside a transaction-scoped context (caller passes `tx`); the caller wraps the operation in `pg.transaction(async (tx) => helper(tx, ...))`. This caller-owns-tx pattern works idiomatically across pglite, supabase-js, postgres-js, and `pg` — see `docs/kb/audit-log.md` for the `withAudit` reference implementation.
- **2026-05-10** — `inet::text` formatting differs between pglite and real Postgres. *Context:* ADR-0006 cycle 2 t6 sub-case AC9.6 — `withAudit({ ip: '203.0.113.5', ... })` round-trip assertion `ip::text === '203.0.113.5'` failed under pglite, which returned `'203.0.113.5/32'` (with `/32` mask). Real Postgres returns the un-masked form. *Why it matters:* Use `host(inet)::text` instead of `inet::text` for the canonical IPv4-string form on both engines. The mask difference is a substrate-rendering quirk only; the stored bytes are identical. If a test fails on `'203.0.113.5'` vs `'203.0.113.5/32'`, it is a formatting drift, not a data integrity bug.
- **2026-05-11** — pglite INSERT and DELETE behave DIFFERENTLY under FORCE RLS with no INSERT/DELETE policy. *Context:* ADR-0034 cycle 3 t5 — `clubs` ships with two policies (SELECT + UPDATE) and explicitly NO INSERT/DELETE policy. The premortem (R1) predicted both would silent-deny (`affectedRows === 0` per cycle 2's documented UPDATE shape). Empirical result on pglite 0.4.5: INSERT raises SQLSTATE 42501 (matches production-Supabase — the implicit `WITH CHECK (false)` denial path), but DELETE silently-denies with `affectedRows === 0` on both axes (FORCE-RLS-no-policy AND REVOKE-GRANT). *Why it matters:* Tests asserting INSERT denial under no-policy MUST assert SQLSTATE 42501 with a SAVEPOINT-recover wrapper (matching cycle 1's AC8.11 pattern — the aborted transaction needs a SAVEPOINT to recover or the next statement fails with "current transaction is aborted"). Tests asserting DELETE denial under no-policy MUST assert `affectedRows === 0` + a service-role post-state read confirming the row still exists. Cycle 2 caught the UPDATE-silent-deny pattern; cycle 3 extended it: UPDATE and DELETE silent-deny, INSERT raises 42501. The INSERT raise is a STRONGER contract than the premortem predicted — production-fidelity for the most-load-bearing axis (anti-forgery on append-only tables).
- **2026-05-10** — pglite GUC visibility inside RLS WITH CHECK clause evaluation is not always reliable, even when top-level `auth.uid()` returns the expected uuid. *Context:* ADR-0006 cycle 2 AC7.5 — under `app_authenticated NOBYPASSRLS NOINHERIT` with `setTestUid(memberA)`, the probe `SELECT auth.uid()::text` returned the expected uuid, but the same connection's `INSERT INTO audit_log (...)` was rejected by `WITH CHECK (auth.uid() IS NOT NULL)` with `new row violates row-level security policy`. Cycle 1's profiles INSERT positive control on the same auth-stub mechanism worked fine — this is an audit_log-INSERT-WITH-CHECK-specific interaction. *Why it matters:* The "app_authenticated authorized CAN INSERT" claim was deferred to production via `it.todo` with a comment pointing at the audit-log KB topic. Future cycles testing positive-INSERT-under-RLS-policy-with-non-trivial-WITH-CHECK should plan for this gap — pin the assertion to a real-Supabase-JWT staging integration in the same cycle, OR split the AC into a structural positive control (service-role + `pg_policies` count + service-role INSERT round-trip) plus a negative WITH-CHECK control (anon -> 42501) that together prove the policy is wired without requiring the GUC-inside-WITH-CHECK path. Cycle 3 (auth + real Supabase) will revisit.

## pg-query-emscripten companion notes

We use `pg-query-emscripten` (libpg_query bindings) for AST-tier shape assertions on migrations.

- **2026-05-09** — pg-query-emscripten emits trigger metadata as numeric bitfields, not keyword strings. *Context:* ADR-0003 cycle 1 t5 attempt 1 — the AST assertion for `profiles_protect_role_change` did a `JSON.stringify(node)` substring match for `'UPDATE'` and failed because libpg_query emits `events: 16` (TRIGGER_TYPE_UPDATE) and `timing: 2` (TRIGGER_TYPE_BEFORE), not the strings `'UPDATE'` / `'BEFORE'`. *Why it matters:* Use bitfield equality for the timing axis (`timing === 2`) and bitwise-AND for the events axis (`(events & 16) === 16`). The TRIGGER_TYPE_* constants are stable across libpg_query 13–16; reference is `src/postgres/include/nodes/parsenodes.h` in the libpg_query repo. This applies to ANY trigger-AST assertion; don't wrap bitfield checks in `JSON.stringify(...).toContain(...)`.
- **2026-05-09** — pg-query-emscripten ships without TypeScript types. *Context:* ADR-0003 cycle 1 t0 — wrote a minimal ambient `tests/db/_fixtures/pg-query-emscripten.d.ts` declaring just the parts we use (`parse(sql: string): { parse_tree: PgParseTree; error: PgParseError | null }`). *Why it matters:* `pnpm typecheck` fails outright without the ambient. Don't reach for `@ts-ignore` or `as any` — the ambient is small and gives downstream tests proper completions on the parse tree.
