## Timestamps + timezone policy

Linked ADR(s): 0034 (timestamp storage in UTC; presentation in club-local time).

ADR-0034 commits the project to four declared timestamp categories — Moments (UTC `timestamptz`), Wall-clock intents (`timestamptz` + `tz_name` companion column), Vendor-derived moments (UTC `timestamptz` from external systems), and Jurisdictional dates (`date` + jurisdiction config). The `lib/time/` module is the single source of truth for `new Date()` / `Date.now()` (via `nowUtc()`) and for `Intl.DateTimeFormat({ timeZone })` (via `formatInZone()` and `formatAuditRowDualZone()`); an ESLint `no-restricted-syntax` rule enforces the single-source-of-truth invariant repo-wide.

## Lessons

- **2026-05-11** — Node 22 ICU silently aliases `'CST'` to `'America/Chicago'` and accepts lowercase zone names like `'America/chicago'` without throwing — `isValidIanaZone()` built on "did `Intl.DateTimeFormat` throw" returns `true` for both. *Context:* ADR-0034 cycle 3 t2 — AC2 sub-case 3 named `'CST'` (abbreviation) and `'America/chicago'` (case-mismatch) as expected-`false` cases. On Node 22.16 Windows, the `Intl.DateTimeFormat('en-US', { timeZone: 'CST' })` constructor does NOT throw — it normalizes the input to `'America/Chicago'` and continues. *Why it matters:* The cheap "does the constructor throw" predicate is looser than the spec assumed. Two fixes are valid: (a) compare the input against `Intl.DateTimeFormat({ timeZone: input }).resolvedOptions().timeZone` and reject if they differ — catches both abbreviation-aliasing AND case-normalization in one check; (b) accept the looser predicate and rely on the CHECK constraint at the application layer plus the audit-log presentation logic. This run shipped (b) and documented the gap in `tests/time/zones.test.ts` as a `FIDELITY GAP` describe block; a future cycle can tighten to (a) without changing the public API.
- **2026-05-11** — `Intl.DateTimeFormat({ timeZone: 'Europe/London', timeZoneName: 'short' })` emits `'GMT+1'` on Node 22 Windows, not `'BST'`. *Context:* ADR-0034 cycle 3 — `formatAuditRowDualZone` AC3 sub-case 8 names `'BST'` as the expected `offset` for a mid-summer Europe/London render. Node 22's ICU on Windows produces `'GMT+1'`; older Node versions and other OS hosts may produce `'BST'` or `'GMT+01:00'`. *Why it matters:* Tests that assert short-zone abbreviations across non-Chicago zones MUST accept the variation — `tests/time/audit-render.test.ts` uses a regex `/BST|GMT\+1|GMT\+01:00/`. The `audit-render.ts` `looksDaylight()` heuristic correctly treats `'GMT+1'` as non-daylight (doesn't match the `D`-or-`BST` pattern), so the `dstSeam: null` invariance for non-DST instants holds across all hosts — but the abbreviation string itself is non-portable for non-CT zones, and any downstream consumer that pattern-matches on `'BST'` will silently miss on Node 22 Windows.
- **2026-05-11** — `nowUtc()` over `now()` — the zone tag is deliberate friction. *Context:* ADR-0034 Open Question 5 — the `lib/time/` helper that wraps `new Date()` was named `nowUtc()` instead of `now()`. *Why it matters:* Six extra keystrokes per call site is the cost; the benefit is that no contributor will plausibly add a sibling `now()` helper with a different zone and import the wrong one by autocomplete. The name documents the contract — "I return a UTC-anchored Date" — and the ESLint rule's error message points at it explicitly ("Use nowUtc() from lib/time/ instead of new Date() — ADR-0034 single-source-of-truth"). If you find yourself reaching for a `now()` alias, you're working around the policy; either the policy is wrong (open a follow-up ADR) or your code shouldn't be calling wall-clock-now at all.
- **2026-05-11** — `date_trunc('day'|'hour'|'week'|'month', x)` MUST pair with `at time zone <zone-literal>` for any report-correctness query — bare `date_trunc` is forbidden under `db/queries/reports/**`. *Context:* ADR-0034 §"Storage and database rules" — Postgres `timestamptz` is stored as UTC, and `date_trunc('day', x)` without an explicit `at time zone` clause produces UTC day buckets, NOT America/Chicago day buckets. A "today's redemptions" report computed in UTC drifts by up to 6 hours from the club-zone day boundary and silently mis-attributes evening transactions. *Why it matters:* The lint script `scripts/lint/sql-day-bucket.mjs` enforces this under `db/queries/reports/**` with a regex + AST-equivalent proximity heuristic (the `at time zone` must appear within ~80 chars of the `date_trunc` match, OR before the next `;`). Day, hour, week, AND month buckets are all gated — the latent-bug surface is "any time-bucketed aggregation," not just day boundaries. Out-of-scope queries (ad-hoc analytics, internal debug) are exempted by directory placement, not by prose. CI wiring is deferred to a harmonized lint cycle; the script ships standalone and is callable as a library via `lintSqlDayBucket({ scope?, files? })`.
