# Admin operations console

Linked ADR(s): 0035.

The `/admin` surface for `manager+` users — eight pages fronting the staff workflows that cycles 1–3 shipped without UI. Source-of-truth for the three-layer defense pattern, the server-action contract, the typed-confirmation dialog convention, and the cross-cutting source-grep tests that police all of it.

## Lessons

- **2026-05-15** — The admin surface uses a **three-layer defense pattern**: middleware path-gate → RSC `requireRole` → DB RLS. *Context:* ADR-0035 AC4–AC6 + the role-ladder-defense test. (1) `middleware.ts` `GATED_PREFIXES` rejects unauthenticated requests at the edge before any server code runs. (2) `app/(admin)/admin/layout.tsx`'s first body statement is `await requireRole('manager')` — the RSC gate that fires on every page render and on every server-action invocation. Every `**/page.tsx` and every `**/_actions/*.ts` ALSO calls `requireRole` as the first await — defense-in-depth, validated by `tests/auth/admin-routes-defense-in-depth.test.ts`. (3) Every table the actions touch (`profiles`, `audit_log`, `feature_flags`, `privacy_requests`) has `ENABLE+FORCE ROW LEVEL SECURITY` with `manager+`-scoped policies — the DB layer rejects any read/write that somehow slipped past layers 1 and 2. *Why it matters:* Any single layer can fail (middleware regex drift, layout refactor losing the first-await, action file forgetting the guard). The three-layer model means all three would have to fail simultaneously for a non-manager to mutate admin state. The meta-test `tests/admin/role-ladder-defense.test.ts` asserts all three layers exist — failure messages name the missing layer with guidance. A future ADR removing any layer "for simplicity" should add a corresponding meta-test relaxation; the current pin assumes all three are load-bearing.

- **2026-05-15** — The `admin-routes-defense-in-depth.test.ts` walker depends on **source order**: helper function declarations MUST live BELOW the default-exported page function. *Context:* ADR-0035 finisher dispatch — `app/(admin)/admin/privacy/page.tsx` and `app/(admin)/admin/verifications/page.tsx` initially declared their `PrivacyQueueBody` / `VerificationsQueue` helper functions BEFORE the default export. The walker's regex-fallback scans for the first `\bawait\b` token in source order and asserts it's followed within 40 chars by `requireRole(`. The first await in those files was `await supabase.from(...)` inside the helper, NOT `await requireRole(...)` in the default export, so the test failed. The fix was surgical: move the helper declarations to AFTER the default export. Function declarations are hoisted, so the JSX reference in the default export still resolves correctly. The pattern matches `changeRole.ts` / `approveVerification.ts` / `openRefundFlow.ts` where the production `defaultDb` adapter sits below the action for the same first-await-token contract. *Why it matters:* The TypeScript-AST walker (preferred) is more robust, but the regex fallback shipped alongside it because libpg_query AST occasionally normalizes in ways the assertion couldn't track. When the AST walker is available the source-order constraint is moot; when it isn't, source order is load-bearing. Document the convention at the top of every admin page file via a header comment: "// Page body MUST appear before helper function declarations — see docs/kb/admin-console.md."

- **2026-05-15** — Admin server actions follow a **first-await `requireRole` + `withAudit`-wrapped mutation** contract. *Context:* ADR-0035 t10–t17 — every mutation action under `app/(admin)/admin/**/_actions/*.ts` ships with this shape: (1) `import 'server-only';` first line. (2) `await requireRole('manager')` as the first runtime statement (or `'owner'` for promotion paths). (3) Self-edit guard (`if (profile.id === session.user.id) throw new SelfEditViolation(...)`) BEFORE the audit-tx opens — zero audit row written on self-edit attempts. (4) Inside `withAudit(action, target_type, target_id, ...)`: `SELECT ... FOR UPDATE` (before snapshot), the mutation, `SELECT` (after snapshot). (5) Post-tx best-effort work (`revalidateTag('admin-dashboard-counts')`, email enqueue stubs) wrapped in try/catch — cache outage cannot roll back the audit-tx commit (premortem R2). (6) `before` / `after` payloads carry ONLY non-PII columns; length-suffixed forms for free-text fields. *Why it matters:* The contract is the substrate for every cross-cutting source-grep test — taxonomy uniqueness, no-PII, role-ladder defense, dashboard cache invalidation, throw discipline. A new admin action that deviates breaks at least one source-grep test (intentional — the tests are the contract). The canonical reference implementations are `approveVerification.ts` (idempotent no-op + sequence-driven member_number) and `approveDeletion.ts` (load-bearing FOR UPDATE order from premortem R10).

- **2026-05-15** — Typed-confirmation dialogs use **raw Radix `AlertDialog`**, not the shadcn wrapper — to preserve focus discipline and ADR-0023 precedent. *Context:* ADR-0035 t14 — `components/admin/typed-confirmation-dialog.tsx` is parameterized by `confirmPhrase` (case-sensitive, whitespace-significant; empty bypasses the input for non-mutation flows like refund-handoff). Initial focus is on Cancel, Esc closes, `aria-modal='true'`. The destructive action button is `disabled` until the typed phrase matches. The shadcn `AlertDialog` is intentionally avoided because the abstraction has historically drifted on focus management — a member-detail dialog that opens with focus on the destructive button is one shipped bug from a real production incident. *Why it matters:* The pattern ships in five places in this cycle (role change, reverification, refund-flow handoff, member deletion, kill-switch flag toggle, privacy approve-export, privacy approve-deletion, privacy reject). One shared component keeps the focus-trap semantics consistent and the axe-core a11y sweep clean. A future contributor who wants to "simplify" by adopting the shadcn wrapper needs to first prove the shadcn version honors Cancel-as-initial-focus and Esc-closes-without-confirm — the current axe-core suite is the regression guard.

- **2026-05-15** — `createAdminClient` (service-role) is allowed inside admin actions via a **scoped `.eslintrc.json` override**, NOT a global rule relaxation. *Context:* Cycle 3 shipped a project-level ESLint rule banning `createAdminClient` outside `lib/`. ADR-0035 admin actions legitimately need service-role for three reasons: (a) `softDeleteProfile` ANONymizes columns that the caller's session can't write under RLS; (b) `nextval('member_number_seq')` cannot be expressed via PostgREST `.update()`; (c) the `admin.session.role_check_denied` audit hook fires on a session that may lack `auth.uid()`. The fix in `.eslintrc.json` is an `overrides` block scoped to `app/(admin)/admin/**/_actions/*.ts`. Premortem R1 added a naming convention: `adminClient` (service-role escape) vs `userClient` (cookie-scoped, RLS-gated) so the reader sees which client is doing what. Source-grep test asserts no `createAdminClient()` call is followed within 20 lines by a `.select(` chain — service-role is for writes/escapes only, reads use the cookie-scoped client so RLS gates them. *Why it matters:* The ESLint rule exists because service-role bypass is the highest-blast-radius footgun in this codebase — one misuse leaks data across tenants forever. Global relaxation is wrong; per-directory override with a sibling source-grep test is the right shape. Future ADRs adding new service-role escape points should add their own override entry with an inline comment naming the ADR.

- **2026-05-15** — Read-only admin actions belong on a **named allowlist**, not implied by absence of audit emission. *Context:* ADR-0035 t21 + the finisher's dashboard-cache-invalidation walker — the test walks every `app/(admin)/admin/**/_actions/*.ts` file, filters out an explicit read-only allowlist (`searchMembers.ts`, `queryAuditLog.ts`), then asserts every remaining mutation-class file (contains `INSERT|UPDATE|DELETE` SQL keywords) contains the literal `revalidateTag('admin-dashboard-counts')`. The first AC35 draft listed ten specific action filenames; premortem R5 surfaced that future actions (e.g., a Slice 5 `expireMembership`) would be invisible to the walker. The generalized walker + named allowlist catches future actions automatically — a new file either invalidates the dashboard or gets added to the read-only allowlist explicitly. *Why it matters:* "Implicit by convention" tests rot the moment a new contributor doesn't read the convention. "Explicit allowlist + walker" tests fail loudly with a clear message ("this new action neither invalidates the dashboard nor appears on the read-only allowlist — add it to one"). The pattern applies to any cross-cutting invariant a worker might forget: cache invalidation, audit event presence, PostHog tagging, Sentry tagging. Keep the allowlist short (read-only actions are rare); keep the walker authoritative.
