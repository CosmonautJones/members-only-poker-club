# PII & privacy

Linked ADR(s): 0009, 0023.

## Lessons

- **2026-05-08** — Risk:high + ADR-0023 cross-link should auto-trigger a mandatory premortem before implementation. *Context:* T1 (`<ConsentProvider>`) for ADR-0024 hit the auto-flag because of its ADR-0023 (privacy/GDPR) cross-reference. The premortem surfaced 12 distinct failure modes — 4 spec-fed (banner copy misrepresentation, SDK pre-consent leak, edge-cache cross-user replay, Essential→auth lockout) and 8 surface-specific (hydration mismatch, cross-tab desync, listener leak, stale closure, re-render cascade, mount→write loop, cookie write race, used-outside-provider). Each mitigation became a code/test contract the worker honored one-for-one. *Why it matters:* privacy/PII surfaces fail silently — the validator can be green at 134/134 while every visitor is being tracked pre-consent, because the test never had the right shape to catch the leak. The premortem is the artifact that turns "what could go wrong" into a checklist of mitigations the implementation is bound to. Keep the auto-flag default for any task that touches ADR-0023, ADR-0009, or consent/auth/PII state.

- **2026-05-15** — Source-grep tests for PII column names in audit `before:`/`after:` literals are cheap, high-signal guards — keep doubling down. *Context:* ADR-0023 first established the pattern; ADR-0035 cycle 4 expanded it across every admin server action. `tests/admin/no-pii-in-admin-audit.test.ts` walks every `app/(admin)/admin/**/_actions/*.ts` file and asserts the regex `/email|full_name|phone|dob|reject_reason:|message:/` does NOT match any `before:` or `after:` object literal in source text. Length-suffixed forms (`reject_reason_length`, `message_length`) are permitted; raw verbatim PII strings are not. *Why it matters:* The audit log is forever-retained (per ADR-0006) — once a PII value lands in `before`/`after` it's there for life of the system, and the soft-delete anonymization machinery in ADR-0023 specifically does NOT scrub historical audit rows. Source-grep at test-time is the only check that catches the value BEFORE it commits to the audit log. The test cost is ~50ms; the cost of catching a leaked email a year later is regulatory. Three additions in cycle 4 made the pattern tighter: (1) verbatim reject reasons ARE permitted in audit (staff-authored, not user-PII) but length-only for `message_length` on `requestVerificationInfo` because the message can contain user PII; (2) `requester_email` in `privacy_requests` is captured pre-anonymization for confirmation email delivery — column-level comment in the migration documents the constraint, plus a source-grep guards against it leaking into audit; (3) PostHog payload allowlist is the sibling guard for the analytics surface — same regex, applied to event property keys instead of audit literals.
- **2026-05-15** — PostHog event payload property keys MUST be an explicit allowlist, not "anything not on a blocklist." *Context:* ADR-0035 premortem R4 — the cookie banner consent gate covers product analytics but does NOT cover identifying staff in cohort reports. Staff who consented at signup would have their email sent to PostHog if `admin_action_attempted` included `actor_email` "for debugging." The fix in `lib/analytics/admin-events.ts` is a TypeScript type that pins the payload shape to `{ role: string, outcome: 'ok' | 'denied' | 'error', queue_depth?: number, flag_key?: string, field?: string }` — no `actor_id`, no `actor_email`, no `target_id`, no `profileId`. The negative test in `tests/admin/posthog-events.test.ts` asserts every event payload is matched against `/email|profile_id|actor_id|target_id|user_id/` and FAILS if any property name matches. *Why it matters:* Allowlists fail closed; blocklists fail open. A worker adding a new admin event with `target_email: 'for debugging'` would pass a blocklist that didn't yet know about that key. The TypeScript type is the first guard; the regex test is the runtime guard for the case where someone uses `as any` to bypass the type. Pair the two — neither alone is sufficient.
