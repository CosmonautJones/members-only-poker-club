# Authentication & sessions

Linked ADR(s): 0002.

## Lessons

- **2026-05-10** — PKCE query-param recovery flow keeps `app/(auth)/reset-password/page.tsx` as a server component; the fragment flow forces `'use client'` + an idle/exchanging/ready state machine. *Context:* ADR-0002 cycle 3 spec C2 — `supabase.auth.resetPasswordForEmail(email, { redirectTo: '<APP_URL>/reset-password' })` with current Supabase ships the recovery `token_hash` as a query string param, NOT a URL fragment. The server component reads `searchParams.token_hash` + `searchParams.type === 'recovery'`, calls `supabase.auth.verifyOtp({ token_hash, type })` server-side, then renders the password form on success or the error state on failure. *Why it matters:* fragments live only in the browser — the server never sees them — so a fragment-based recovery flow MUST be a client component that runs `verifyOtp` post-hydration, with a state machine for the idle → exchanging → ready transitions and an explicit guard against the fragment being missing on first paint. The query-param flow eliminates the entire client-state-machine concern. If a future cycle re-reads Supabase's docs and finds the recommended flow has flipped back to fragments, the page MUST become `'use client'` AND the spec MUST be amended BEFORE the cycle runs — `searchParams.token_hash` will silently be `undefined`, and the page will render the "this page is for password recovery" fallback message instead of erroring. Pin the current flow in spec C2 at the time of write.
- **2026-05-10** — `middleware.ts` MUST set `x-pathname` (and `x-search`) on `request.headers` BEFORE calling `lib/supabase/middleware.ts updateSession()`, NOT after — otherwise the header does not propagate to RSCs that read it via `next/headers`. *Context:* ADR-0002 cycle 3 t2 + revise iter 1 — `updateSession` builds the forwarded response via `NextResponse.next({ request })`, which freezes the request-header set at call time. Worker iter 1 set `x-pathname` after `updateSession` returned; the middleware tests passed (they asserted the header value, not the call ordering); but `requireRole.ts` and `app/(member)/layout.tsx`, which read `headers().get('x-pathname')`, both got `null` and the `?next=` preservation silently broke. *Why it matters:* This is the only reliable way to preserve the destination URL through Next.js's middleware → RSC boundary — server actions cannot read `request.url` directly, and `next/headers` is the only RSC-side primitive that can see request headers. Revise iter 1 added an explicit ordering pin to the middleware test (`mockImplementationOnce` captures `request.headers.get('x-pathname')` at the moment `updateSession` is invoked) — the test fails if `x-pathname` is unset when `updateSession` runs. The read-side splits `x-pathname` and `x-search` into two separate headers and concatenates with `encodeURIComponent(pathname + search)` — keeping them separate makes the middleware-side write trivial (no string concat) and the RSC-side read explicit about query-string handling. Cycle 5 (staff layouts, first production callers of `requireRole`) inherits this contract.
- **2026-05-10** — Signup orphan recovery is a fail-loudly contract, NOT an auto-cleanup. *Context:* ADR-0002 cycle 3 t3 — signup's `supabase.auth.signUp(...)` succeeds first, then attempts the `profiles` INSERT via `createAdminClient()`. If the profile INSERT fails, the action returns a generic FormError and writes a structured log line carrying the orphan `auth_user_id`, but does NOT call `auth.admin.deleteUser(auth_user_id)` and does NOT retry. *Why it matters:* the orphan-reaper job needs an admin runtime + a queue + a retention policy + a way to discriminate "INSERT failed because of a transient DB hiccup" from "INSERT failed because the user is mid-signup-replay" — none of those exist in cycle 3. Auto-cleanup with that uncertainty would silently delete legitimate accounts. The "fail loudly" posture is the load-bearing safety property: an orphan is recoverable by support; a silently-half-completed signup that masquerades as success is not. Sub-case 7 of `signup-action.test.ts` pins the contract — "log fired with the orphan id" + "FormError returned" + "NOT redirected". Cycle 4 picks up the reaper.
- **2026-05-10** — `lib/auth/safeNext.ts` lives in `lib/auth/` (NOT inlined in `login/actions.ts`) AND carries `import 'server-only';` — open-redirect defense has no business in a client bundle. *Context:* ADR-0002 cycle 3 revise iter 1 — worker iter 1 inlined the validator at `app/(auth)/login/actions.ts:40-47`. Critic-diff flagged it: future callers (signup `?next=`, magic-link callback, OAuth callback) cannot import an inlined function — they'll either copy/paste it (drift surface) or skip the defense. *Why it matters:* The rejection list `[empty, non-string, non-leading-slash, '//', '/\\', '://']` IS the defense surface. Drift between two copies (one in login, one in OAuth) is exactly how open-redirects ship. Lift the helper to its own module the moment a second caller is plausible — even if the second caller doesn't exist yet. The `import 'server-only';` line carries the same load-bearing posture as `errors.ts`: a future refactor that imports `safeNext` from a client component would compile cleanly and ship the validator to the browser without it; the directive throws at the boundary instead.
